# Phase 1 — Content OS (days 31–120)

**Goal:** one closed loop — idea → published → measured — running on the Tue/Fri rhythm without Paras touching anything except camera and final approval.

**The headline:** six of the nine agents already exist. This phase is mostly wiring plus a memory layer, not invention.

| Weeks | Focus | Lands |
|---|---|---|

**Weeks 9–10 are the real test of this phase.** Everything before is preparation for it. If the loop cannot run one week without Paras in it, the phase has not landed regardless of how many agents are marked done.

## Build in public, throughout

One agent = one long-form + one short + one LinkedIn post + one Skool drop. Twelve agents over thirteen weeks maps almost exactly onto two publishes a week.

The Wednesday live workshop becomes the **live build session** — the agent that week, built in front of people. That is the single highest-value change to the existing schedule: it converts a delivery obligation into content, proof, and product development simultaneously.

See [`../03-build-in-public/content-series-plan.md`](../03-build-in-public/content-series-plan.md).

## Revenue during Phase 1

Content OS does not sell anything. Revenue comes from three places while it is being built:

1. **4C Workshops and Programmes** — the Sprint 0 motion, continued. ₹1.5–4L and ₹8–25L per engagement at benchmark, warm and referral. Highest ticket, fastest close.
2. **Lead Engine, manual** — carried over from Sprint 0, still 30 min/day, still Paras-reviewed
3. **The Wednesday workshop** — now also the live build session, and where enterprise buyers self-qualify
4. **First 4C Installs**, sold manually — the *high-ticket manual version of the thing being automated*

Point 3 is the model working as intended: sell the manual version while building the automated one. Revenue arrives first, and every install is a live test of agents that eventually become product.

---

## Exit criteria

0. **Revenue moved.** Monthly revenue is materially above the ₹1–5L it started at, from workshops, programmes and the first install. This is criterion zero because at 3–6 months of runway a quarter that produces systems but not revenue shortens the runway by a quarter.
1. **The loop ran one full week hands-off** — Paras on camera and approvals only
2. **Two publishes a week held for 13 weeks.** Missed publishes are the failure signal, not slow builds
3. Every one of the nine has a current spec in `04-agents/` and a named human QA
4. Scorekeeper has 13 weeks of data and Monday planning demonstrably responds to it
5. At least eight agents have 30+ days of real use — packageable under the build-once-sell-twice rule
6. First DFY install sold and delivered, with a case study captured

---

## What would make this phase fail

- **Building instead of publishing.** More commits than videos in a week is the early warning.
- **Paras staying in the loop** because it is faster than fixing the lane. It is faster this week and it is why the system never runs without him.
- **Skipping Scorekeeper** because the numbers are uncomfortable early. The loop only compounds if last week changes this week.
- **Starting Commerce OS agents early** because sales feels more urgent. Manual Commerce is fine for 90 days; a half-built Content OS is not.
